One prompt, three models, two games

The same instruction, sent word for word to three models at high effort, one run each, twice — once for Tetris and once for Space Invaders. Nothing was edited afterwards. The files below are what came back.

The prompts

PROMPT.txt — round one

Write a playable Tetris as a single self-contained HTML file.

No external references of any kind: no CDN, no web fonts, no images, no network.
It must work when the file is opened directly from disk in a browser.
Arrow keys to play.

Output only the contents of the HTML file. No explanation, no markdown fences.

PROMPT_invaders.txt — round two

Write a playable Space Invaders as a single self-contained HTML file.

No external references of any kind: no CDN, no web fonts, no images, no network.
It must work when the file is opened directly from disk in a browser.
Arrow keys to play.

Output only the contents of the HTML file. No explanation, no markdown fences.

Two words apart, and nothing else. Each is read from its file by the script and handed to all three models unchanged, so nobody can retype it slightly differently and quietly ruin the comparison. Everything the models disagree about below, they disagree about from the same starting point.

Read them again after the tables. Neither one says score, levels, sound, high score or start screen.

Counting tokens, they are nowhere near each other. Both numbers are true. They are measuring different things.

The tokens you cannot see are the ones the model spent thinking. The file is what is left at the end. If you bill by output — and you do — then a short file is not the same as a cheap one, and a repository full of short files tells you nothing at all about what they cost to produce.

And then the same prompt, with a team — Opus 5, ultracode

Everything above is one agent given the prompt once. This is the same prompt, the same model and the same effort run under ultracode, which is Claude Code's multi-agent orchestration: the model organises a group of agents and works the problem in stages. Six agents instead of one.

Nearly three times the tokens for a third more code. 3251 lines written to keep 1296 — three whole games read once by something that was not a person, and thrown away.

And it really is better

This is the part that would be dishonest to leave out. The merging agent read all three and found three bugs neither builder had mentioned: the saucer's held hum was killed by pause and never came back; the life counter dropped while the wreck was still burning instead of after it; the title screen was still running the in-game HUD, so it showed you the previous game's score. It fixed all three. The verifier then ran the result for 17.6 simulated minutes of random input with pauses, blurs, tab-hides and stalls, and it did not throw.

None of that is nothing. An orchestration of agents caught what a single pass did not, and the argument for doing it is real.

And nobody read any of it. Not the three that were thrown away, not the 22 features nobody asked for, not the three bugs — you have my word for those, which is exactly the problem. The code got better and the amount of it a person has looked at stayed at zero.

Three numbers, not a ranking

One run per model per game. In the DEG practical you will be told that a two-fold change with n = 1 is an observation and not a result; the same applies here. Run the same prompt on the same model twice and you get different code. The second game exists because of that — and it disagreed with the first, which is the point.

You can check a Tetris by playing it for five seconds. That is why this is a fair thing to accept without reading. You cannot check a mapping rate by looking at it — and that is the whole difference.
